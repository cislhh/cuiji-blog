我把 `mattpocock/skills` 这个仓库从头翻了一遍，39 个技能，每个 `SKILL.md` 都读了，又对着 1.3.2 的更新记录核了一遍。

结论先说：这套东西不是给你一套流程，是给你一堆小规矩。它不接管你从提需求到上线的整条路，它只在你做某个具体动作的时候站在旁边说"这一步这么做才算做对"。所以你随时可以改它、违反它、只挑一个用。

这个差别很重要。GSD、BMAD、Spec-Kit 那一路的做法是"我把流程拿走，你按我的走"——听起来省事，但流程一旦不合你的意，你只能在它的规则里绕，改不动。而这套东西每个技能的正文也就几十到一百多行，你看一眼就知道它在要求什么，不爽就直接改。

下面是我读完觉得真正值得记下来的部分。

## 一、它想治的四个毛病

README 把失败模式列成四条，整套技能基本就是围着这四条长出来的。

| 毛病 | 长什么样 | 它的解法 |
| --- | --- | --- |
| 它没做我要的 | 你觉得自己说清了，交付出来完全不是那回事。问题出在开头没聊透，不在模型笨 | 开工前一轮一轮追问，问到你没有默认假设为止 |
| 它话太多 | 二十个词说一个词的事。项目里的词没定下来，它只能临场猜 | 建一份共用的词表，把难反悔的决定写成 ADR（一条短记录，只说当初为什么这么定） |
| 代码不 work | 需求明明聊清楚了，写出来还是不对。缺的是一条能马上告诉你"错了"的反馈回路 | 先写会红的测试，再写刚好够用的实现 |
| 越写越乱 | agent 让写代码变快，也让代码库变复杂的速度变快 | 定期挑一块，把行为往小接口后面收 |

前两条是沟通问题，后两条是工程问题。有意思的是它没有把四条都做成"流程"，而是每条只给一两个动作。比如"它话太多"这一条，解法不是"让 agent 说话简洁点"——那种要求写一百遍也没用——而是建词表。词定了，变量名、文件名、测试名跟着一起定，话自然就短了。

## 二、一条主线，三条岔路

九成的需求走这条线：

**追问 → 合成 spec → 拆票 → 逐张实现（或整本并行）→ 两栏 review → 复盘**

拆开说：

- `grill-with-docs` 负责把"要做什么"问到没有默认假设，顺手把词定下来。
- `to-spec` 把上一轮的结论合成为一份 spec（一份写清"要做什么、怎么算做完"的说明）。它的定义就是**不再问你**——很多 agent 会忍不住再问一遍，把聊透的东西重新搅浑。
- `to-tickets` 把 spec 拆成一小片一小片能从头跑到尾的活，每片声明自己被谁卡着。
- `implement` 一张一张做，内部跑测试和 review；`implement-spec` 是整本一起推，能并行的并行。
- `code-review` 从两个角度看这个改动：符不符合仓库写下来的规矩，以及是不是忠实实现了当初要的东西。
- `retro` 复盘。它改的是 agent 的环境，不是代码。

另外三条岔路，只是入口不同，最后都并回主线：

- 别人提的 bug 和需求 → `triage`。先复现验证，再问清楚，产出一份能直接开工的说明。
- 难 bug、变慢、偶发失败 → `diagnosing-bugs`。先造一条"在这个 bug 上会变红"的回路，没有回路不许猜原因。
- 大到一个会话装不下的活 → `wayfinder`。把路画成一张决策地图，一张一张解，直到能看清怎么走。

岔路的价值在于：它们不会各自长出一条流水线。所有活最后都汇到同一条主线上，你不需要记五套流程。

## 三、两个开关：为什么有些技能模型永远调不动

这是整套设计里唯一一条不能松的规矩，也是最多人没搞懂的地方。

技能分两种：

**只有你能敲的。** 文件里写着 `disable-model-invocation: true`。模型看不见它，别的技能也调不动它。描述写成给你看的摘要，不带"什么时候用我"这种触发词。代价是你得记住它存在，好处是一分上下文都不占。

**模型也能自己拿的。** 不写那个字段。描述是写给模型的"什么时候来拿我"，要带足触发场景。代价是这段描述一直挂在上下文里，每轮都在花钱；好处是它能被自动抓、也能被别的技能调用。

这两种是可以互换的：一件事做成"模型能自己抓"，就是拿你的记性换上下文；做成"只有你能敲"，就是反过来。`/ask-matt` 这个总入口存在的唯一理由，就是把"十几个手动技能记不住"这件事收成一个。

然后是那条硬边界：**只有你能敲的技能，永远不能被别的技能调用。**

1.3.0 为此专门修过一轮。当时有几个技能在正文里写"如果没有配置，就调用 setup-matt-pocock-skills"，但那个技能恰恰是"只有你能敲"的，模型根本调不动，这个调用不可能成功。现在的写法统一成："如果没有，**让用户去跑** /setup-matt-pocock-skills"——这是给人看的指令，不是给模型的调用。

同一轮还改了另一件事：正文里写 `/grilling` 只是句闲话，模型不一定会真的加载；写成"调用 Skill 工具，名字是 grilling"命中率高得多，而且去掉斜杠以后不绑死某个客户端。你看，指路的话怎么写，直接决定它会不会去看。

## 四、grill 家族：十一个入口，差别在三个坐标

名字里带 grill 的、以及内部会跑追问的，一共 11 个。它们不是"语气轻重"的区别，而是三个坐标上的不同组合：**问的是什么、会不会写进文件、什么时候算问完**。

先讲清楚最核心的那个动作，因为其余十个都是它的包装或者变体。

### 追问到底在干什么

它把你的不确定画成一棵决策树：每个决定都会分叉出依赖它的下级决定。

关键在于**一轮只问"现在能问的"那批**——原文管这个叫 frontier，前沿。判断标准是：这个问题的前置条件是不是都已经落定了。落定了，现在问不会瞎猜；没落定，问了也是浪费，因为答案会依赖本轮另一个还没定的问题。

这条规矩直接决定了体验：你答完一轮，定下来的决定会把边界往外推，解锁后面依赖它的问题。所以好的追问是一轮一轮往前推的，不是一口气甩你二十个问题。

还有两条容易被忽略的：

- **每题都要带建议，措辞要让"是"等于接受建议。** 这样你一个词能确认十个决定，不用每次从零想。这不是替你决定，是给你一个可以反驳的靶子。1.3.2 专门调过这块措辞，就是为了避免出现"我同意"其实等于回答了"不"。
- **事实是它的活，决定是你的。** 某个问题需要看文件、看工具输出，它应该派个子任务去查，而不是问你。而且不该因为它在查就整轮卡住——只有依赖那个事实的下游问题才等它。

什么时候算问完？这一轮问空了，等于树上每个分支都走过了，没有东西被悄悄假设。而且，在你确认达成共识之前，它不许动手。

### 十一个入口怎么分

| 入口 | 问什么 | 写文件吗 | 什么时候用 |
| --- | --- | --- | --- |
| `grilling` | 一个计划、决定、想法 | 不写 | 你就想要这套访谈纪律本身 |
| `grill-me` | 同上 | 不写 | 你不在仓库里，比如打磨一份方案、一篇稿子 |
| `grill-with-docs` | 同上 | 写词表和 ADR | 你在仓库里。**有仓库就用它**，它严格更好 |
| `wait-what` | 不追问，重讲上一句 | 不写 | 上一句没听懂 |
| `to-questionnaire` | 问"怎么发出去"，不问主题 | 写问卷 | 答案在别人脑子里 |
| `triage` | 别人提的 issue / PR | 写分诊记录 | bug 和需求堆起来了 |
| `wayfinder` | 一个大到看不清路的活 | 写地图和决策票 | 一个会话装不下 |
| `improve-codebase-architecture` | 你选中的那个改造候选 | 写临时目录的报告 | 你想动一块代码，但不知道接口该长什么样 |
| `loop-me` | 你反复做的一个流程 | 写流程说明 | 想把一件重复的事交出去 |
| `writing-fragments` | 你到底在注意什么 | 写碎片 | 有话想说，但不知道写成什么 |
| `writing-shape` / `writing-beats` | 这篇到底在论证什么 | 写文章 | 素材有了，要收成一篇 |

最容易搞混的是三个：`grill-me`、`grill-with-docs`、`wayfinder`。

- `grill-me` 的前提不是"什么都不知道"。它假设你心里已经有一个东西，哪怕很糊，缺的是问穿。如果你连"要解决谁的什么问题"都没有，第一轮就会卡在你也答不出来的问题上——那种情况该先用 `research` 补事实，或者用 `to-questionnaire` 去问知情的人。
- `grill-with-docs` 跟 `grill-me` 跑的是同一套访谈，区别是它会顺手把词写进 `GLOSSARY.md`、把难反悔的决定写成 ADR。所以在仓库里，它永远比 `grill-me` 好——同样的时间，多留下纸面痕迹。
- `wayfinder` 不是"更狠的追问"，它解决的是另一个问题：路本身看不见。它的产物是"决定"，不是"交付"。走完地图要接 `to-spec`，不能直接 `implement`，否则地图里链起来的细节全丢。

三条判据，按顺序问：一个会话装得下吗（装得下就别用 wayfinder）→ 现在能不能把问题说精确（不是"能不能答"）→ 需要别人或别的会话接着干吗（需要就得写下来）。

### 最容易犯的六个错

1. 在仓库里用 `grill-me`，什么都不写下来，下个会话从零开始。
2. 一轮抛十五个问题，里面一半依赖另一半的答案。
3. 让 agent 问你查得到的事实。
4. 追问完直接 `implement`，跳过合成 spec 那一步。
5. 拿 `triage` 去处理自己刚拆出来的票——那些票本来就该直接开工。
6. 把 `wait-what` 当成"说得再详细点"。它要的是换一种讲法：补上下文、说人话、用你项目词表里的词。同一套黑话再详细一遍，只会更听不懂。

## 五、这套 skill 自己是怎么写出来的

如果你想自己写技能，答案全在 `writing-for-agents` 这一个里。它是这套仓库的母技能，另外 38 个都是照它的规矩写的。这部分也是我觉得最值得搬走的。

### 1. 文档都在花两种钱

一种是**上下文**：入口文件的每一行、每个"模型能自己拿"的技能的描述、每个被塞进上下文的文件。每一轮都在付费。

另一种是**记性**：有哪些文档、什么时候该用哪个。你本人就是索引。

这两种是可以互换的。所以判断一个东西该做成哪种技能，只需要问：模型有没有可能自己需要它？有没有别的技能需要调它？两个都没有，就别让它常驻，做成"只有你能敲"。

### 2. 指路的话，措辞决定它会不会去看

所谓"指路的一句话"，就是上下文里的一句引用，后面挂着没在上下文里的材料，**而且这句话本身要说清"什么时候该去看"**。

技能的描述是这种话，入口文件里一行"XX 见 docs/xxx.md"也是。四条规矩：

- 东西再好，话说得含糊就等于没写。先改措辞，改不好再考虑把材料搬进来。
- 关键词往前提。触发词埋在第三行就废了。
- 一个分支一个触发词。两个词说同一件事，其实是同一个分支写了两遍。
- 删掉"本技能帮助你……"这种自我介绍，正文已经在干这件事了。

### 3. 一份文档里该有三层

第一层是照着做的步骤，第二层是随手要查的规则，第三层是推出去、等用到再加载的参考。

推出去不是为了省 token，是为了让最上面那层还能读。判断标准很土但很好用：**每个分支都要的写在原地，只有某些情况才会走到的推出去。**

这里有个词叫 sprawl，摊大饼：每一行都还有效、都不重复，但文档就是太长，注意力被摊薄了。

### 4. 每一步都要能判断"做完了没有"

做完的判据有两个旋钮：清楚不清楚，要求高不高。

模糊的边界（"达成理解"）会诱使它提前收工——注意力滑向"我完成了"，而不是"我做对了"。所以 `diagnosing-bugs` 第一阶段的判据写得特别硬：四条可以打勾（能抓住这个 bug、稳定复现、秒级、不用人盯），后面跟一句"没有这条命令，不许进第二阶段"。

最好的判据是既能打勾、又足够穷尽。

### 5. 一个词换一整片行为

这些词模型训练时都见过：紧回路、红、曳光弹、深模块、战争迷雾。你说一个词，它调出一整套做法；你自造一个词，得先花一段话解释，它还未必照做。

原文给了一个改写练习：

- "快、稳定、开销小" → **紧**（一条紧回路）
- "一条你信得过的回路" → **红**（把模糊的门槛变成二选一：这条回路在这个 bug 上会变红，或者不会）

还有一条容易反着做：别用"不要做什么"来引导。那等于把那个行为拖进上下文，还让它更显眼——"别想大象"，满脑子都是大象。要正面说该做什么，让不该发生的那句根本不出现。

### 6. 修剪：一件事只说一遍，别抄环境，别攒垃圾

- **一件事只说一遍。** 重复同时抬高维护成本和 token，还会把这件事的重要性虚抬。
- **别抄环境。** `package.json` 的脚本、配置文件、目录结构本身就是答案，你在文档里复述它，那叫缓存。只缓存看文件看不出来的：没写下来的约定、某个选择的理由、配置里没承认的坑。
- **越放越沉。** 没用的行有两种来路：从来就跟任务无关，或者世界变了它没跟着变。沉积是默认命运——加进来觉得安全，删掉觉得危险，层层叠到你得打钻才找得到还活着的部分。
- **废话指令整句删。** 模型默认就会遵守的话，说了等于没说。判断标准是对模型而言，不是对读者而言。两个人吵这是不是废话，其实是在吵"默认到底是什么"，跑一遍就知道。

## 六、1.3.2 改了什么

先记个数：现在是 39 个技能——工程 20、生产力 7、in-progress 8、misc 4，另外有一个 `deprecated` 是空桶（退役的技能直接删，删它的更新记录会写清谁替代了它）。

in-progress 里多了一个 `software-factory`（1.3.1 之后加的），给"软件工厂"这件事定共用词：任务、触发、一次运行、运行机、工单系统、调度器……它反复强调三条刹车（自动检查、自动评审、人工评审），以及"一次只加一个自动触发，先掐着量跑"。你只是想让 agent 帮你做一次活，用不上它。

更新记录一共 20 条修订，我认为会影响日常使用的有这么几条。

**`ask-matt` 改成先读再答。** 它在讲某个技能做什么、或建议跳过某一步之前，必须先去读那个技能的 `SKILL.md`，不能凭自己的一句话摘要下判断。摘要跟原文对不上，它就会指错路。

**`code-review` 改了三处。** 一，它会主动在仓库里搜"该怎么写代码"的文件，`CODING_STANDARDS.md` 和 `CONTRIBUTING.md` 一律交给"规范"那栏；二，两个子任务改成前台跑、直接用它俩返回的报告（之前是后台）；三，tracker 通过配置好的说明文档解析，不再写死一条路径。

**`tdd` 提 seam 要带说明。** 每个建议的接缝（seam，不改那里代码就能改变行为的位置）附一句"它抓得住什么、漏掉什么"，选的时候不用靠猜。

**`diagnosing-bugs` 多了一道保险。** 第五阶段：如果你是靠"故意把代码改坏"逼出红色的，要先跟没改过的副本 diff 一遍，确认那一改真的改到了东西，再相信这个红。有些改动静悄悄什么都没改，却让测试显示失败——这种假红会把你带到错的方向。

**`to-tickets` 支持子 issue。** 来源是一个已有 issue 时，每张票做成它的子 issue；用原生阻塞关系表达依赖时，就不再写"Blocked by"那一节。

**`wayfinder` 收了四处。** 地图和票不再打"可开工"这类分诊标签（它们是决定，不是活）；交叉引用只用真实 issue 号（占位符会自动链到不相干的 issue）；研究分支只推不合并、不开 PR；解票时按标签写的类型来解。

**`setup-matt-pocock-skills` 改了两批。** 写 tracker 之前先确认远程仓库真的连得上；发现旧的 `CONTEXT.md` 会提议改名成 `GLOSSARY.md`；缺的分诊标签会帮你建；GitHub 那套改成先读 PR 正文再看评论、用原生参数表达阻塞、并给出"数一数还有几个没解"的命令。**跑完升级要重跑一次**，刷新 `docs/agents/`。

**派子任务的技能统一要求"干净窗口"。** `implement-spec`、`code-review`、`codebase-design`、`improve-codebase-architecture`、`wayfinder`、`research`、`grilling`、`chief-of-staff` 都写明了：给每个子任务开一个新的上下文窗口，不要从当前对话 fork 出去。有些客户端默认就是 fork，而 fork 恰好把子任务存在的意义扔掉了——它本来该不带你的包袱去看。

**`chief-of-staff` 的记忆改造。** 改成一个小 wiki：一个索引加每个主题一页，靠"吸收、查询、体检"三个动作维护。而且它写的是历史，不是现在——每条结论带日期，涉及代码的注明"在哪个提交上为真"，旧的被取代时不改写、只标注。

其余是边角：`teach` 的工作区改成写在你在的目录、测验答案位置随机；`handoff` 明确写出 `$TMPDIR`、没有就 `/tmp`；`wizard` 的模板修了两批（回车保留旧值不再带引号、写 `.env` 用单引号保命、软链接也能写、输入遇 EOF 报错而不是死循环）；GitHub 的工单模板明确告诉 agent，issue 只能提到你自己的仓库，绝不许提到上游。

顺带说一句 1.3.1 那条：`ask-matt` 不再说 `diagnosing-bugs` 修完要交接给 `improve-codebase-architecture`（那一步被删了）。现在修完之后指你去 `retro` 问"什么能防住它"，只有结论是"缺 seam"时才指去 `improve-codebase-architecture`。

完整的 20 条在仓库的 `CHANGELOG.md` 里，逐条带 PR 号和原因，值得自己过一遍。

## 七、如果你想开始用

先跑一次 `setup-matt-pocock-skills`。每个仓库一次，它会问你三件事：工单放在哪、分诊用什么标签、领域文档放哪。跑完之后它会写几个说明文件，告诉后面所有技能"这里的活在哪、怎么找"。

然后，如果只做三件事：

1. **把 `grill-with-docs` 变成默认起手式。** 任何不琐碎的需求，第一句就是它。它同时治"它没做我要的"和"它话太多"，而且是唯一一个顺手把词表建起来的入口。
2. **把 `retro` 的产物变成检查，不是文档。** 再写一篇规范的边际收益很低。真正的收益在把"同一类错第三次发生"变成一条 lint 规则、一个一致性测试、一个 CI 任务。
3. **只守一条：大段文本不进主上下文。** 大段 diff、日志、后端代码交给子任务，或者在沙箱里算完只打印结论。这一条同时解决"上下文被撑爆"和"它读到一半忘了前面"两个问题。

## 八、几个我认同、但用起来容易走样的地方

**深模块和"别过度封装"是同一把尺子。** 原文说得很清楚：深度是接口的属性，不是实现的行数。它给了一个删除测试——想象删掉这块，复杂度消失了，那它是纯中转，该删；复杂度在 N 个调用点重现，那它在挣饭吃，该留。很多"多层封装"的问题不是层数多，是删除测试为负。

**"AI 会自己遵循深模块吗？默认不会。"** 代码生成是局部最优，深模块是全局约束。四个把手按有效程度排：接缝写进 spec、review 的规范那栏、确定性检查、词表。别指望它理解深模块，要让它没机会写浅模块。

**上下文该清就清，别舍不得。** 追问 → spec → 拆票是一条思路，中间清掉等于让它拿着二手摘要重新推理，别清。但票与票之间，上一张的上下文就是垃圾，该清。判断顺序是：能继续吗 → 上下文跟下一段无关吗 → 需要交接吗 → 能不能不用人盯地做完 → 否则压缩。除了"继续"，每个动作都在把一手材料换成二手材料，只有留下来的成本更高时才值得换。

**机械性的问题做成检查，别写成文档。** 这条是 `retro` 的核心分类纪律，也是我觉得最容易被忽略的一条：能用一行正则或一段语法树判出来的，就是机械型，做成 lint 或测试；需要"看看周围怎么写"的，才是判断型，留给文档。文档靠人记，检查靠机器跑，而 agent 每次开工都只能重新读文档，还会忘。

**它不让你更快，它让你少返工。** 追问那一轮花的时间，通常比返工一次便宜。拆票花的时间，通常比在一坨改动里 debug 便宜。
