一、先看结论：四句话 + 它想治的四个毛病

先说清楚它不是什么。它不是那种"从提需求到上线全包"的流程框架（GSD、BMAD、Spec-Kit 那一路）。那类东西的毛病是：它把流程拿走自己管，流程一旦不合你的意，你只能在它的规则里绕，改不动。

这套东西反过来：每个 skill 只钉住一个动作该怎么做，做完就退出，不接管你整条路。所以你随时可以改它、违反它、只挑一个用。看懂它，只要记住四句话。

① 它是纪律，不是流程

一个 skill 只回答"这件事怎么做才算做对"。

流程引擎出了 bug 你只能绕；纪律你看一眼就知道该怎么改。/tdd 只讲红绿循环、测试写在哪、哪三种测试是白写的，它不管你怎么开分支；把活串起来的是 /implement，不是它。

你想让 agent 在某个动作上稳定做对，就抽一个 skill。

你想让它"自动把整个需求做完"，别指望单个 skill。

② 触发权分两种，不能混

有些 skill 只有你亲自敲才生效，有些模型能自己伸手拿。

这不是风格问题，是成本问题。模型能自己拿的那种，描述要一直挂在上下文里，每轮都在花钱；只有你能敲的那种不占地方，代价是你得记住它存在。混着做，就会两头吃亏。

要串流程、要你拍板的，做成"只有你能敲"。

别给"只想手动跑一次"的东西写自动触发词。

③ 先有词，才有短话

一个词顶一整片行为：紧回路、曳光弹、深模块、战争迷雾。

这些词模型在训练时见过，你说一个词，它就调出一整套做法；你自造一个词，得先花一段话解释，它还未必照做。词定下来以后，变量名、文件名、测试名会跟着一起定，话自然就短了。

你发现自己反复用"快、稳定、开销小"这种三个词描述同一件事时，找个现成的词把它收掉。

别为了造词而造词，先找现成的。

④ 上下文是有限的，指过去比搬进来便宜

能让 agent 顺着一句话自己找到的，就别塞进上下文。

常驻的材料按"token × 轮次"收费。入口文档只放指路的一句话，细节留在文档里等着被查；模型本来就会做的事，你写一遍等于白写还占地方。

大段规范、设计稿、历史决定，写成"在哪、什么时候去看"。

别用"以后可能有用"的理由留常驻文本。

它想治的四个毛病

README 里把失败模式列成四条，整套 skill 基本就是围绕这四条长出来的。

毛病表现它的解法对应的 skill
它没做我要的你觉得自己说清了，交付出来完全不是那回事。问题出在开头没聊透，不在模型笨。开工前先一轮一轮追问，问到你没有默认假设为止。/grilling /grill-me /grill-with-docs
它话太多二十个词说一个词的事。项目里的词没定下来，它只能临场猜。建共用的词表，把难以反悔的决定写成 ADR。词定了，命名跟着定。/domain-modeling（/grill-with-docs 会用）
代码不 work需求明明聊清楚了，写出来还是不对。缺的是一条能马上告诉你"错了"的反馈回路。把先写会红的测试变成纪律，再写刚好够用的实现。/tdd /diagnosing-bugs
越写越乱agent 让写代码变快，也让代码库变复杂的速度变快。定期挑一块把行为往小接口后面收，让改动以后只落在一处。/improve-codebase-architecture /codebase-design
一句话总结：先用追问把"要什么"问死，用词表把"叫什么"定死，用先写测试把"对不对"锁死，用模块设计把"以后还敢不敢改"保住。剩下三十多个 skill，都是这四件事在不同场景下的入口。

二、全景：一条主线、三条岔路、一层词、一圈独立工具

下面这张图是 39 个技能的位置图。实线 = 产物往下传，虚线 = 可以被调用或者旁路。颜色：紫=主线（你手动敲），青=模型能自己拿的基础件，琥珀=岔路，玫红=随叫随到的独立工具。

这张图怎么读

  • 主线只有一条：追问 → spec → 拆票 → 逐张实现（或整本并行）→ PR → 复盘。任何"做需求"的活，最后都落在这条线上。
  • 岔路只是入口不同：别人提的 bug 从 /triage 进；难 bug 从 /diagnosing-bugs 进；大到看不清路的活从 /wayfinder 进。它们最后都汇回主线，不会各自长出一条流水线。
  • 词表层不是工具，是语言：/tdd、/codebase-design 本身不产出流程，它们定义"什么叫好测试""什么叫深模块"。主线里的 skill 靠这些词互相说话。
  • 独立工具不排队：/handoff、/wait-what、/teach 跟某个需求无关，是随手用的。

三、两个开关：哪些要你亲自敲，哪些模型能自己抓

这是整套设计里唯一一条不能松的规矩。搞懂它，你就不会再问"为什么我让它自己用 /to-spec，它不用"。

只有你能敲的（文件里写着 disable-model-invocation: true，Codex 那边是 policy.allow_implicit_invocation: false）：模型看不见它，别的 skill 也调不动它。描述写成给你看的摘要，不带"什么时候用我"这种触发词。代价是你得记住它存在；好处是一分上下文都不占。

模型也能自己拿的：不写上面那两个字段。描述是写给模型的"什么时候来拿我"，要带足触发场景。代价是这段描述一直挂在上下文里；好处是它能被自动抓、也能被别的 skill 调用。

判断只有一句：模型有没有可能自己需要它？有没有别的 skill 需要调它？两个都没有，就做成"只有你能敲"，别付那份常驻开销。

硬边界（1.3.0 为此专门修过一轮）：只有你能敲的 skill，永远不能被别的 skill 调用，哪怕正文里写着"调用 setup-matt-pocock-skills"。所以 /to-spec、/to-tickets、/triage、/code-review、/wayfinder 里统一写成："issue tracker 应该已经给你了；如果没有，让用户去跑 /setup-matt-pocock-skills"。那是给人看的指令，不是给模型的调用。

谁真的会调谁

四、这套 skill 自己是怎么写出来的

你想自己写 skill，答案不在某一个具体技能里，在 /writing-for-agents。它是这套仓库的"母技能"：另外 38 个、入口文件、docs/agents/*.md，全是照它的规矩写的。这一章是全文最值得搬走的部分。

4.1 文档都在花两种钱

花的是是什么怎么省
上下文
模型每轮都要读		入口文件的每一行、每个"模型能自己拿"的技能的描述、每个被塞进上下文的文件。每一轮都在付费。挪到一句话后面；删掉废话；只在某些情况才需要的，推出去等用到再看。
记性
你要记住多少		有哪些文档、什么时候该用哪个。你本人就是索引。不是越少越好——它是"你还能做主"的价格。需要你判断的地方留着；不需要判断的地方（用一个总入口，或者让模型自己抓）把它消掉。

这两种成本是可以互换的。一件事做成"模型能自己抓"，就是拿你的记性换上下文；做成"只有你能敲"，就是反过来。/ask-matt 这个总入口存在的唯一理由，就是把"十几个手动技能记不住"这件事收成一个。

4.2 指路的话，措辞决定它会不会去看

所谓"指针"，就是上下文里的一句引用，后面挂着没在上下文里的材料，而且这句话本身要说清"什么时候该去看"。技能的描述是指针，入口文件里一行"XX 见 docs/xxx.md"也是同一个东西。

  • 东西再好，话说得含糊就等于没写。必须有材料的地方配了一句软话，先改措辞；改不好再考虑搬进来。
  • 关键词往前提。指针的活儿就是触发，触发词埋在第三行就废了。
  • 一个分支一个触发词。两个词说的是同一件事，其实是同一个分支写了两遍，合并掉。
  • 删掉"本技能帮助你……"这种自我介绍。正文已经在干这件事了，重复一遍只占地方。

4.3 一份文档里该有三层

层放什么例子
① 照着做的步骤按顺序执行的动作/diagnosing-bugs 的六个阶段；/to-tickets 的五步。
② 随手要查的规则定义、清单、判断标准。平铺一堆同级规则是正常的，不算乱/tdd 的三条反模式；/code-review 的十二条代码坏味道。
③ 推出去的参考放到另一个文件，等用到再加载tests.md、mocking.md、DESIGN-IT-TWICE.md、PHASE-BOUNDARIES.md。

推出去不是为了省 token，是为了让最上面那层还能读。最干净的判断标准是"分支"：每个分支都要的，写在原地；只有某些情况才会走到的，推出去。同一个概念的定义、规则、注意事项要放在同一个标题下，别散在三处。

这里有个词叫 sprawl（摊大饼）：每一行都还有效、都不重复，但文档就是太长，注意力被摊薄了。解法还是分层，按分支或者按顺序切开。

4.4 每一步都要能判断"做完了没有"

做完的判据，就是告诉 agent "这一步到此为止"的那句话。它有两个旋钮：

  • 清楚不清楚：能不能一刀切出"做完"和"没做完"。模糊的边界（"达成理解"）会诱使它提前收工——注意力滑向"我完成了"，而不是"我做对了"。后面还看得见的步骤会形成拉力，判据的清不清楚就是阻力。防御顺序：先把边界收紧（便宜、就地能改）；只有边界本来就模糊、而且你确实见过它赶工，才用"拆成两段、把后面的步骤藏起来"——而且"藏"只在真的换了上下文（交接、派子任务）时才行，同一个会话里藏着没用。
  • 要求高不高：它逼你做多少。"每个改到的模型都要交代清楚"能逼出彻底的工作，"产出一份变更清单"不能。

所以 /diagnosing-bugs 第一阶段的判据写得那么硬：四条可以打勾（能抓住这个 bug / 稳定复现 / 秒级 / 不用人盯着），后面还跟一句"没有这条命令，不许进第二阶段"。最好的判据是既能打勾、又足够穷尽。

4.5 什么时候该拆，什么时候别拆

  • 按顺序拆：后面的步骤会诱使它赶工时切开。反过来也成立——把步骤合并，等于提前把"后面还有多少活"暴露给当前这一步。
  • 按调用方式拆（只对 skill 说）：只有当"有一个独立的词该单独触发它"或者"别的 skill 要调它"时，才拆出一个"模型能自己拿"的技能——因为你要为多出来的那段常驻描述付费。
  • 总入口：手动技能多到你记不住时，用一个总入口把它们收在一起（/ask-matt）。它只能提示，永远触发不了那些手动技能。

4.6 一个词换一整片行为

所谓关键词，就是模型训练时已经见过的紧凑概念。它跑文档时拿这些词思考：紧回路、红、曳光弹、战争迷雾、深模块、seam。这些词以单词形式反复出现（而不是每处都重新解释一遍），会在它脑子里累积成一个定义，用最少的字锚住最完整的行为。

原文给的改写练习：
  • "快、稳定、开销小" → 紧（一条紧回路）
  • "一条你信得过的回路" → 红（把模糊的门槛变成二选一：这条回路在这个 bug 上会变红，或者不会）

好处是双份的：字更少，而且给了模型一个更锋利的挂钩。原文的建议是——假设你文档里每一处三元组、每一句"描述一个概念"的话，都在等着被一个词收掉。

否定的坑：用"不要做什么"来引导，等于把那个行为拖进上下文，还让它更显眼——"别想大象"，满脑子都是大象。要正面说该做什么（"写一行注释说明为什么"），让不该发生的那句根本不出现。禁令只留给"实在没法正面说的硬护栏"，而且必须同时给出正面的目标。

4.7 修剪：一件事只说一遍，别抄环境，别攒垃圾

概念什么意思动作
一件事只说一遍一个意思只存一处。重复同时抬高维护成本和 token，还会把这件事的重要性在层级里虚抬。合并到一处，别处只留一句话指过去。
环境就是答案，别抄package.json 的脚本、配置文件、目录结构、--help 的输出，本身就是答案。你在文档里复述它，那叫缓存。只缓存"看文件看不出来的"：没写下来的约定、某个选择的理由、配置里没承认的坑。
越放越沉没用的行有两种来路：从来就跟任务无关（纯介绍、本该推出去的分支），或者世界变了它没跟着变。沉积是默认命运：加进来觉得安全，删掉觉得危险，层层叠到你得打钻才找得到还活着的部分。定期逐行问一句"这句现在还跟这份文档要干的事有关吗"。
废话指令模型默认就会遵守的话，说了等于没说，还付了成本。判断标准是对模型而言，不是对读者而言：两个人吵这是不是废话，其实是在吵"默认到底是什么"，跑一遍就知道，别辩论。不合格就整句删，别在词上抠。要仔细打不过默认，换个更狠的词（死磕）。

4.8 拿这把尺子量量自己写的 skill

查什么怎么问典型改法
描述分对层了吗这个技能需要模型自己抓吗？需要别的技能调它吗？只在点名时用的，做成"只有你能敲"，描述去掉触发词、写人话；要被自动抓的，保留触发场景。
有没有废话"注意代码规范""要写测试"——模型默认不做吗？删掉，换成能打勾的判据（"每个新增模块必须有对应的接口测试"）。
每一步有判据吗每步结尾能不能二选一判断？把"确认设计合理"换成"列出这次的 seam，跟我确认；没确认不许写测试"。
是不是把别处的文档抄进来了同一个意思是不是在技能和设计文档里各有一份？技能里只留一句话指过去 + 什么时候去看。
有没有关键词你在提示里反复说同一串三个词吗？把它提成正式术语写进词表，技能里只重复这个词，不重复解释。

五、grill 家族：同一个动作，十一种入口

这是整套仓库里最容易被用错、也最值钱的一块。名字里带 grill 的、以及内部会跑追问的，一共 11 个。它们的差别不是"语气轻重"，而是三个坐标：问的是什么、会不会写到文件里、什么时候算问完。

5.1 一句话分清

入口问的是什么产出什么时候你会喊它

5.2 先纠正一个常见误解

/grill-me 的前提不是"空白目录 + 不知道要做什么"。它假设你心里已经有一个东西——一个想法、一份计划、一个设计草稿，哪怕很糊——缺的是把它问穿。如果你连"要解决谁的什么问题"都没有，第一轮就会卡在你自己也答不出来的问题上。那种情况更该先用 /research 把外部事实补齐，或者用 /to-questionnaire 去问知情的人，而不是硬问。

真正的"迷茫"有三种，分属三个不同的技能：

哪种迷茫你此刻的状态该用为什么
① 问题没想清"我想做点什么，但不知道要解决谁的什么问题。"先别问。/research 补事实，或者 /to-questionnaire 问业务方，或者 /teach 先把这行学会。追问只负责把已有的想法问穿，它不负责替你长出问题。
② 想法有，边界不清（小）"我知道要做这件事，但归属、流程、验收标准全没定。"有仓库 → /grill-with-docs；没仓库 → /grill-me规模在一个会话之内，缺的只是决定。
③ 目的地有，路看不见（大）"我知道要去哪，但会牵动几十个文件，不知道从哪下手。"/wayfinder路线本身是未知的，而且一张地图要跨多个会话、多个 agent 共享。
一句话分清：追问的产物活在这次对话里；wayfinder 的产物活在 issue tracker 里。
/grill-me 什么都不写，会话一关就没了（所以在仓库里一律用 grill-with-docs，把词和决定落到词表和 ADR）；wayfinder 把思考搬到外面，写成地图加决策票，别的会话、别的 agent、三天后的你都能接着干。

三条判据，按顺序问

  1. 这个活一个会话装得下吗？装得下 → 永远别用 wayfinder（原文自己说它"更慢更密"）。装不下 → 才轮到它。
  2. 现在能不能把问题说精确？注意不是"能不能回答"。能说精确 → 它是一张票、或一个追问问题；说不精确 → 它是雾。雾多到看不清路，才是 wayfinder 的地盘。
  3. 需要别人、别的会话接着干吗？需要 → 产物必须写下来并共享；不需要 → 对话里的共识就够了。

两个容易搞混的细节

  • wayfinder 内部也在跑追问，但它跑两轮，而且第二轮是横着扫（扫整个空间，找出还开着的决定和"现在就能走的第一步"）；grill-me / grill-with-docs 是竖着往下剥。所以可以记成：wayfinder = 追问 + 搬到地图上 + 决策票分类 + 跨会话。
  • wayfinder 不产出交付。它的票是"决定"，不是"活儿"。地图走完要接 /to-spec 收敛，不能直接 /implement。而追问完之后，是可以动手的。

5.4 一个一个说清，它们到底差在哪

① /grilling —— 唯一真干活的那个

它的思路：把不确定的东西画成一棵树，然后一层一层剥。每个决定都会分叉出依赖它的下级决定。这一轮能问的（原文叫 frontier，前沿）就是"前置条件都已经落定、现在问不会瞎猜"的那批问题。一轮只问这一批，每题编号，并且附上"我建议选哪个"，然后把决定权还给你。

为什么非要一轮一轮来：你这一轮的回答会改变树——定下来的决定把边界往外推，解锁后面依赖它的问题。所以"答案依赖本轮另一个还没定"的问题，属于下一轮，这轮问了也是浪费。这条规矩决定了后面所有内嵌用法的形态。

为什么每题都要带建议：措辞要让说"是"就等于接受建议。这样你一个词能确认十个决定，不用每次从零想。这不是替你决定，是给你一个可以反驳的靶子。

事实和决定要分开（最容易被违反的一条）：查事实是它的活，永远不是你的。某个问题需要看文件、看工具输出，就派个子任务去查，别问你。而且不要因为它在查就整轮卡住——只有依赖那个事实的下游问题才等它，这一轮剩下的现在就问。

什么时候算完：这一轮问空了，等于树上的每个分支都走过了，没有东西被悄悄假设。而且：你确认达成共识之前，它不许动手。

② /grill-me —— 不留痕的那个入口

整个技能只有一句正文：去调 grilling。它存在的唯一理由是给"不在工作目录里"这件事一个名字——你在打磨一份计划、一个设计、一篇要发出去的东西，底下没有仓库可写。

它跟 grill-with-docs 的关系是严格被压一头的：在仓库里，grill-with-docs 跑同一套访谈，还额外留下纸面痕迹，所以永远更好。反过来，在没有仓库的地方用 grill-with-docs，它会想写文件却写不了。

③ /grill-with-docs —— 追问的副产品是把词钉死

它干的事：同一套访谈，但边问边做两件附带的事——domain-modeling 负责挑你用词的毛病、逼你想清边界情况、把结果写进词表和 ADR；grilling 负责问。

它真正在做的不是"写文档"，而是通过让你把词写下来，逼你把概念想清楚。这跟第二个毛病（话太多）是一件事的两面：共用的词不是文档产物，是思考的压缩器。词定了，变量名、文件名、测试名一起定，代码库对 agent 更好找路，想事也更省字。

写文件这件事，它的规矩很克制：

  • GLOSSARY.md 用到才建——第一个词真的定下来时才建文件。
  • 词当场写，不攒着。
  • 词表里绝对不许写实现细节。它不是 spec，不是草稿纸，不是决定仓库，它只是词表。
  • ADR 只在三个条件同时成立时才提：很难反悔、没有背景的人看了会惊讶、确实是取舍的结果。缺一个就不写。
  • 发现你说的话跟代码不一致，当场点出来（"你代码里取消的是整张单，你刚说可以部分取消，哪个对？"）。

④ /wait-what —— 不是"再说详细点"，是"换一种讲法"

它是事后补救，grill-with-docs 是事前预防。触发场景是"停，上一句我没落地"。它要求三件事：补一点上下文、说人话（简化技术英语）、用词表里的词（仓库里有多个上下文时，跟着索引找到对的那份词表）。

注意：它只用词表，不改词表。真正的修法是回去补一次 grill-with-docs，让共用的词从源头上就建立起来。

⑤ /to-questionnaire —— 问"怎么发出去"，不问主题

这是整个家族里最反直觉、也最值得学的一个设计。当答案不在你脑子里，你没法把它问出来。但这个技能说：你永远答得上来的是另外两件事——这东西发给谁，和你需要拿回什么。所以访谈只做这两步（各一轮），然后问卷的问题瞄准"收件人知道而你不知道"的那道缝。

文档结构也是设计过的：目的 / 发件人收件人 / 一段够用的背景 / 怎么答（含截止时间和"可以写不知道"）/ 按主题分组、最重要的放前面、一题一个想法、下面留作答位、只在可能被误解时加一句"为什么这重要" / 结尾一句兜底。

为什么强调"最重要的放前面"：异步意味着你可能只有一次机会。这跟追问的"只问这一轮能问的"是同一个思路，换了介质。

⑥ /triage —— 先验证，再问

它把 issue 当成状态机推：2 个类别（bug / 需求）+ 5 个状态（待分诊 / 缺信息 / 可开工 / 要人做 / 不做），每条 issue 恰好各带一个。

顺序是关键：先验证，再问。bug 要按报告里的步骤复现；PR 要切过去跑一遍相关测试。验证完再追问，产出的东西强得多。它还有两个便宜但常被跳过的前置检查：是不是已经实现了（按领域概念搜代码）和是不是已经被否过（读范围外记录）。已经实现的走"不做"，但不写范围外记录——那是"被拒需求"的档案，写进去会污染去重。

最后产出一份"能开工的说明"，写作纪律值得单独记：写耐久的东西而不是精确的东西（写接口、类型、行为契约，不写文件路径和行号）、描述行为不描述过程、验收标准完整且能独立验证、明确划出范围外。

⑦ /wayfinder —— 两轮完全不同的追问

它的思路：找路，不是冲终点。先给目的地起名（目的地决定每张票长什么样），这一步用追问加深挖；然后第二轮横着扫，把整个空间扫一遍，翻出还开着的决定和"现在就能走的第一步"。

这里有一套很精确的词，都值得进你自己的词表：

  • 决策票：子 issue，持有一个问题，它的解决是一个决定，不是一个交付物。除了地图本身，票分四种：research（不用人盯，派子任务）、prototype（要人一起看，做个粗件）、grilling（要人一起聊，默认）、task（唯一"做"而不是"决定"的类型，靠"解开某个决定的阻塞"获得存在资格）。
  • 战争迷雾：看得见要来、但现在还说不精确的东西，写在地图的"还没说清"那一节。判断标准是"现在能不能把问题说精确"，不是"现在能不能答"。能说精确就是票（哪怕被卡着），说不精确就是雾。别提前把雾切成票那么大。
  • 出界：不是雾。目的地定了范围，越界的是范围问题，不是清晰度问题，单独一节，永远不放出去。
  • 认领：先把票分给自己再动手——分给谁就是认领，没分就是还开放。
  • 一个会话只解一张票（研究票除外）。

它的产出是决定，不是交付。"想直接动手"通常正是你走到地图边缘、该交棒的信号。

⑧ /improve-codebase-architecture —— 先扫描，后追问

它把追问放在后半段：先按 git log 找最近改得多的区域（理由很实在：改得勤的地方，改起来顺手的收益最大），派子任务自己去逛（不套死板的检查表），用删除测试判断哪些是空壳，输出一份临时目录里的自包含 HTML 报告（每个候选一张卡：涉及文件 / 问题 / 方案 / 好处 / 前后对比图 / 强度标记）。然后才问你："你想深入哪一个？"——选中之后进追问，边上边补词、补 ADR。

它明确不做的事：不先给接口方案（那是选定之后 /codebase-design 里"设计两次"那一环）；不列举每个理论上能改但被 ADR 禁掉的东西；不假装能救一个陈年老坑。

⑨ /loop-me —— 把追问对准"你反复做的事"

beta，但它给了一套很好的委托词汇：循环（一生中反复出现的模式）、触发（事件还是定时，事件通常更省）、检查点（人必须确认或决定的地方）、往右推（把检查点尽量往后挪：先把活干完，让人只在最后被问一次，而且那时一切都备好了）、简报（检查点给人看的是"可以直接拍板"的摘要，不是草稿）。

它最反套路的一条：什么都可以不要。一个流程不需要 AI、不需要检查点、不需要排期，除非问下来证明它需要。

⑩ 写作三件套 —— 同一个动作的正反两用

先挖后收是两个独立的技能，各有明确边界：/writing-fragments 只把可能写的东西摊开（碎片可以杂、只要对作者自己有可读性、用 --- 分隔、只加不覆盖）；/writing-shape 和 /writing-beats 只收（把素材当采石场，一次只写一块）。

它们贡献了一个很好的概念：接地——每个概念要么是读者本来就懂的，要么在前面某一块里交代过，否则这一块就把读者丢了。于是"哪些当前提、哪些在文中交代"成了核心取舍：前提要太多会挡住读者，文中交代太多会让开头淹死在定义里。

5.6 一轮真实的追问长什么样

下面这个场景是虚构的，只为了让你看清格式：一个业务模块要从 A 域搬到 B 域，需求方只说了"迁过去"三个字。正确的第一轮长这样——只问这一轮能问的，每题带建议，措辞让"是"等于接受建议。

❓ Q1 - 归属：搬过去之后，这几条业务线归新模块还是留在原模块？

词表里对"模块归属"有定义：谁的列表归谁所有，不由别的模块代管。现在这几条业务线的代码挂在老模块目录下，搬完以后接口、页面、取数配置是不是整体搬？

按定义走：业务线归谁，模块就归谁 → 全部搬到新模块，老模块只留跳转入口；不保留两份代码。

❓ Q2 - 地址：URL 跟不跟着变？

有三种选法：(a) 只留新地址，(b) 新旧并存，(c) 旧地址重定向到新地址。另外提醒一句：一级路由如果要在三个地方分别注册，漏一个就是"权限有、菜单不显示"。

选 (a) 新地址单入口 + 旧地址重定向；理由是后端按路由名授权，双路由会同时养两套权限点。你要是想保住旧书签，就改 (c)。

❓ Q3 - 单据形态：搬完还是"先申请、后审批"两段吗？

现在的约定是：申请阶段没有经办人、没有审批节点，审批单建了才有。迁移会不会改变流转起点（比如只能从已完成的单子发起，还是进行中也能发起）？

两态不动，只改归属；流转起点维持原样。理由：节点来源刚刚统一过，不在这次搬迁里再动。

❓ Q4 - 列表页要不要一起搬？

一起搬，所有列表页的取数、配置、角色要跟着重排，这是整个活的大头；不搬，就会出现"申请页在新模块、列表页在老模块"的半吊子状态。

一起搬，但拆成独立的一张票（被单据迁移卡着），单独验收。理由：半吊子状态对 agent 找路的伤害，大于一次性搬完的成本。

❓ Q5 - 验收按哪一档？

这次是纯结构搬迁，行为不该变。要不要出完整的验收报告？

最轻那档：类型检查 + 受影响的单测 + 一份"迁移前后路由/菜单对照表"人工核对；不出完整报告。

注意这五题的关系：Q1 定归属，Q2 依赖 Q1，Q3、Q4 依赖前两个的答案，Q5 依赖 Q4（搬不搬列表页决定验收量）。所以严格说，真正属于第一轮的只有 Q1 和 Q2——这正是那条"依赖未定问题的题留到下一轮"的规矩。上面写成五题是"预告"，真实跑起来它只会先问两个。

/ask-matt 你敲 总入口

/setup-matt-pocock-skills 你敲

这套技能假设"issue 存在某个地方"。它不猜，先探（远程仓库、已有的 AGENTS.md / CLAUDE.md、词表、ADR 目录、本地 issue 目录、monorepo 的迹象），再一段一段问你，最后写 docs/agents/*.md，并且更新已有文件里的段落，而不是新建一个（CLAUDE.md 已经存在就绝不另建 AGENTS.md）。

新仓库第一次用这套工程技能之前。

/grill-with-docs 你敲

一边追问一边把需求聊定，顺手把领域词钉死（词表 + ADR）。

见第五章。核心是"通过要求你把词写下来，逼你把概念想清楚"。它调 grilling 一次、domain-modeling 两次，分别在不同阶段。

把想法、模糊需求、甚至一段抱怨丢给它，然后一轮一轮回答。边答它会边写词、边提 ADR（只在那三个条件都成立时提）。

有仓库的地方，几乎永远用它，而不是 grill-me。整套东西里回报最高的一步。

纯工具性改动（改文案、修样式）——没有决策树可走。

/to-spec 你敲

把当前对话合成 spec，发到 issue tracker。它明确不再访谈你。

定义就是"不问"。为什么值得单独成一个技能：很多 agent 会忍不住再问一遍，把已经聊透的东西重新搅浑。它只在两件事上要你确认：测试的 seam（"这几处符合你的预期吗？"）和 spec 最终内容。

① 逛仓库（用词表、尊重 ADR）→ ② 先画 seam，优先用已有的、尽量用高的，理想情况只有一个 → ③ 按模板写：问题 / 方案 / 很长的用户故事编号表 / 实现决定（不写文件路径和代码片段）/ 测试决定 / 范围外 / 备注 → 打上可开工标签，不必再分诊。

多会话的活，追问结束、同一个会话里紧接着做。

一个会话能做完的小改动——直接 implement。

/to-tickets 你敲

把 spec 拆成"一小片能从头跑到尾"的票，每张声明自己被谁卡着。

三条铁律：竖着切（每一层都切到，不是横着一层一刀）、做完能演示或验证、一张票塞得进一个干净的会话。而且先做"让改动变容易"的预重构——先变容易，再做容易的改动。宽重构是例外：一次机械改动炸开全库（改列名、改共享类型）时不能切小片，要走"先加新的（不破坏）→ 按影响范围分批搬 → 最后删旧的"，每批一张票。

① 取上下文（可以给 spec 路径或 issue 号）→ ② 逛仓库、找预重构机会 → ③ 切竖片 + 标依赖 → ④ 把拆法列成编号清单让你过一遍（粒度对不对？依赖对不对？要不要合并或再拆）→ ⑤ 发布。本地就是 .scratch/<特性>/issues/NN-名字.md，按依赖顺序编号，卡人的排前面。

接在 to-spec 后面；或者你已经有清楚计划，只需要拆。

一句话能说完的改动。

如果来源是一个已有 issue，每张票做成它的子 issue；用原生阻塞关系表达依赖时，就不再写"Blocked by"那一节。

/implement 你敲

按一张票（或一份 spec）实现：在说好的 seam 上跑 tdd，收尾跑 code-review，然后提交。

它自己几乎不含纪律，全部外包给 /tdd 和 /code-review。这就是"技能是纪律、编排是薄壳"。它还规定了检查节奏：经常类型检查、经常跑单个测试文件、最后跑一次全量。

传票号或路径 → 它先报出票的标题 → tdd → 类型检查/测试 → code-review → 提交到当前分支。

多会话项目里的每一张票；或单会话的小需求。

活还没拆到"一张票说得完"的程度——回去拆票。

传进来一个票引用，它会先去 tracker 取回来，开工前念一遍标题；引用有歧义就问你。调 tdd 和 code-review 统一改成"调用 Skill 工具"的写法，不再写裸斜杠。

/implement-spec 你敲

一次实现整份 spec：把票当依赖图，在能开工的那一圈并行派子任务，全部落到一条集成分支。

关键认知：票不是步骤清单，是带依赖的图，所以任何时刻都有一圈"可以领"的票。沟通要稀疏，主要靠指针（spec、票、笔记、之前的提交），别复制已有信息。每个实现者在自己 worktree 上：确认基于集成分支 → 调 tdd → 完成前把集成分支最新提交合进来（让后续合并是快进）→ 由合并子任务合入。

需要 tracker 已经配好。只有 tracker 用 PR 关活、或者你要求时，才开草稿 PR，而且要在第一次合并之后（零提交的分支开不了 PR）。

spec 大到你想"编排建造"而不是"亲自逐票开车"，而且票之间真有并行度。

只有两三张串行票——逐张 implement 更省。

/wayfinder 你敲

把一个大到一个会话装不下的活，画成 tracker 上的决策票地图，一张一张解，直到路清楚。

见 5.4⑦。三条最容易被忽略：只产出决定不产出交付（"想直接动手"是走到地图边缘的信号）、一个会话只解一张票（研究票除外）、给人看的地方一律用名字（一墙 #42 #43 #44 是没法读的）。还有两个词要分清：战争迷雾（在范围内但还不精确）和出界（范围外，永远不放出来）。

两种模式：画地图（给一个松散想法：定目的地 → 横着问一遍 → 建地图 → 建现在能说清的票 → 第二遍连依赖 → 给研究票派子任务）和走地图（给地图：加载低分辨率视图 → 选票 → 认领 → 按类型解 → 写结论、关票、往"已定的事"追加一行 → 把新露出来的雾放进去）。

全新项目、跨系统大改造、方向本身还没定的大特性。

范围清楚的中等需求（太重）；已经知道怎么做的活。

地图和票都不再打"可开工"这类分诊标签（它们是决定，不是活）；交叉引用只用真实 issue 号（占位符会自动链到不相干的 issue）；研究分支只推不合并、不开 PR；解票时按票上标签写的类型来解。

/triage 你敲

把 issue / PR 沿状态机往前推：分类、验证、必要时追问、写出能开工的说明。

见 5.4⑥。两个便宜但常被跳过的前置检查：是不是已经实现了（已实现走"不做"，但不写范围外记录）、是不是已经被否过（读范围外记录）。另外每条分诊评论都必须以"这条是 AI 在分诊时生成的"开头。

自然语言指挥（"看看有什么要我处理的""把这条移到可开工"）。快速改状态时会跳过追问，并问你要不要补一份说明。

bug 报告、别人提的需求、外部 PR 堆积时。

自己刚拆出来的票（本来就该直接开工）；已经在做的活。

/improve-codebase-architecture 你敲

扫一遍代码库找"能把行为收进小接口"的地方，出可视化 HTML 报告，你挑一个再进追问。

见 5.4⑧。它先定范围再扫：改得勤的地方优先（git log 找热点）。报告写到系统临时目录，文件名带时间戳，不进仓库，然后帮你打开。

每个候选一张卡：涉及文件 / 问题 / 方案 / 好处（用"改动集中"和"调用者省事"来讲）/ 前后对比图 / 强度标记（强 · 值得看看 · 只是猜想）。最后给"我会先做哪个"。只在跟 ADR 冲突时标出来，不列举所有理论上的改法。

隔几天跑一次，当体检。你感觉"这块改起来越来越绕"时。

指望它把陈年老坑拆干净——原文说得很直白：它是体检，不是抢救。

/retro 你敲

会话复盘：改进 agent 的环境，不是改进代码。

六个方向：导航（指针）、自动检查（lint/类型/测试/文件系统）、编码标准、全局入口文件、工具开销（token 用得冤的调用）、信息可达性（把 dev server 日志接出来、只读访问三方服务）。最重要的一条分类纪律：编码标准违规先分类——机械性的（固定语法、被禁 API、import 形状、文件位置）一律做成确定性检查（linter 规则 / 提交前钩子 / CI），文档只留给真正需要判断的。而且：一个连护栏都没有的仓库本身就是一条发现。

在要复盘的那个会话里跑（清空之后再跑，就只剩日志了）。它先调 writing-for-agents 拿写法，再读一手材料，按严重度排序给你建议。

一个会话做歪了之后；或者你发现"同一个错犯了三次"。

刚做完一个顺利的小改动——没有可提炼的环境问题。

机械 vs 判断，怎么分、各自落到哪：
  • 机械型（有固定形态、机器能判）→ 做成检查：eslint 规则 / 一致性测试 / 提交前钩子 / CI。判据很土但很好用：能用一行正则或一段语法树判出来的，就是机械型。
  • 判断型（跨文件一致性、"跟周围风格一致"、命名品味）→ 才写进文档，交给 review 阶段的人和 agent 判断。
  • 为什么优先做成检查：文档靠人记、检查靠机器跑；而 agent 每次开工都只能重新读文档，还会忘。

6.2 工程 · 模型也能自己抓的（9 个）

/tdd 模型可抓

红→绿循环的参考手册：什么算好测试、测试放哪、三种反模式、循环的规矩。

它把"测试"从覆盖率改造成规格：好测试读起来像一条规格（"用户可以拿着有效购物车结账"），代码全改了它也不该改。seam 是你观察行为的公共边界，测试只住在这里，而且只写在事先说好的 seam 上——写任何测试之前，先把 seam 写下来跟你确认。三条反模式：跟实现绑死（mock 内部协作者 / 测私有方法 / 绕开接口查数据库，特征是"重构就红但行为没变"）、同义反复（期望值用跟实现一样的方式重算，构造上就不可能不一致）、横着切（先写完全部测试再写实现，你测的是想象出来的行为）。

先红后绿；一次一片（一个 seam、一个测试、一个最小实现）；重构不属于这个循环，它属于 review 阶段。形状不确定时调 /codebase-design 拿词（它是参考，不是要跑一遍的会话）。

所有"造行为"的活；修 bug 时也用它把回归锁住。

纯样式、纯文案、纯配置搬家。

提 seam 的时候，每个 seam 要配一句"它抓得住什么、漏掉什么"，让你选 seam 不是靠猜。

/code-review 模型可抓

对着一个固定点做两栏 review：规范（符不符合仓库写下来的约定）+ 需求（是不是忠实实现了原始 issue/spec）。两个子任务各看一栏。

为什么必须分两栏、而且不许合并排序：一个改动可以过一栏挂另一栏——完全合规但做错了事，和完全按要求做了但违反约定。合并排序会让一栏掩盖另一栏。最后只给"每栏几条 + 每栏最严重的一条"，不许挑一个跨栏总冠军。

① 定住固定点（commit / 分支 / tag / 合并基点，没给就问）→ 用三点 diff，先确认 ref 能解析、diff 非空 → ② 找需求来源（提交里的 issue 号 → 你给的路径 → docs/、specs/、.scratch/ 下匹配分支名的文件 → 都没有就问）→ ③ 找规范来源（CODING_STANDARDS.md / CONTRIBUTING.md 必须在列），再叠加十二条 Fowler 坏味道基线（仓库文档永远压过基线，坏味道永远只是"可能是"、不是硬违规，工具已经强制的跳过）→ ④ 同时发两个子任务（各限 400 词）→ ⑤ 原样分栏呈现。

分支 / PR / 收尾；/implement 和 /implement-spec 都会自动调它。

只想瞥一眼"有没有明显 bug"——那就直接问，不用走这套。

它会在仓库里主动搜"该怎么写代码"的文件，CODING_STANDARDS.md / CONTRIBUTING.md 一律交给"规范"那栏；两个子任务改成前台跑、直接用它俩返回的报告（之前是后台）；tracker 通过配置好的说明文档解析，不再写死一条路径。

/diagnosing-bugs 模型可抓

难 bug / 性能回退的六阶段诊断循环。

第一阶段就是全部。"如果你有一条在这个 bug 上会变红的紧回路，你就会找到原因；二分、假设检验、插桩都只是在消费它。"所以第一阶段要花不成比例的力气，并且拒绝在没有回路时进第二阶段——"跳去猜假设，正是这个技能要防的失败"。完成判据四条可打勾：能抓住这个确切症状（不是"没报错"）、稳定、快（秒级）、不用人盯。

造回路的十种手段（失败测试 → curl → 命令行 fixture diff → 无头浏览器 → 回放抓包 → 最小 harness → 属性/fuzz → 二分 → 差分 → 最后才是人机脚本）。之后：复现并最小化（删到"去掉任何一个都变绿"）→ 生成 3-5 个可证伪的假设（每个都要说得出"如果 X 是原因，改 Y 会让它消失"），先给你看再测 → 一次只改一个变量，调试日志加统一前缀方便一次清干净 → 在正确的 seam 写回归测试 → 清理并复跑原回路。

一眼看不出原因的、间歇性的、两次已知状态之间溜进来的回归。

明显拼写错误、日志里已经写明原因的错。

第五阶段多了一步保险：如果你是靠"故意把代码改坏"逼出红色的，要先跟没改过的副本 diff 一遍，确认那一改真的改到了东西，再相信这个红——有些改动静悄悄什么都没改，却让测试显示失败。

/domain-modeling 模型可抓

主动去建、去磨项目的领域模型：挑用词的毛病、用边缘情况压它、就地更新词表和 ADR。

它是主动纪律，不是"读一眼词表"（那只是一行习惯，谁都能做）。五个动作：跟词表冲突时当场指出来、把模糊的词锻成规范的词、编一个具体场景逼你说清边界、跟代码对一遍、就地写词（不攒批）。词表里绝不含实现细节。

ADR 只在"很难反悔 + 没有背景的人会惊讶 + 确实是取舍"三条同时成立时才提，其余跳过。词表用到才建。

一句话里有三个意思（"账户"同时指客户、用户、账号），或者一个决定会让以后的人问"当初为什么这么干"。

只是需要"用对词"——读一眼词表就够了，不用开这个技能。

/codebase-design 模型可抓

设计深模块的共用词汇：大量行为藏在小小接口后面，放在干净的 seam 上，通过接口测试。

七个词要原样用，别换成 component / service / API / boundary：module（任何有接口和实现的东西，故意跟大小无关）、interface（调用者必须知道的一切：签名 + 不变式 + 顺序约束 + 出错方式 + 配置 + 性能特征）、depth（接口处能拿到多少）、seam（不改那里代码就能改变行为的地方）、adapter（填进 seam 的具体东西，说的是角色不是材质）、leverage（调用者得到的）、locality（维护者得到的：改动、知识、验证都集中在一处）。四条原则：深度是接口的属性、删除测试（想象删掉它：复杂度消失了=纯中转；复杂度在 N 个调用点重现=它在挣饭吃）、接口就是测试面、一个 adapter 是假设的 seam，两个才是真的。

两份配套参考：DEEPENING.md（按依赖类型给替换策略）和 DESIGN-IT-TWICE.md（并行 3 个以上子任务，各自一个激进不同的约束，最后按 depth / locality / seam 位置比较，并给出自己的推荐）。

要设计模块接口、找深化机会、决定 seam 放哪、让代码更好测也更好找路。

只是要把一个函数写对——用不着这套词。

/prototype 模型可抓

一次性代码，只回答一个问题。先按问题选分支。

问题决定形态。问"这套逻辑/状态模型对不对"→ 单文件可分享 HTML（能点、能切场景）；问"这应该长什么样"→ 同一路由上放几个结构上真的不一样的变体，用参数切换。两个分支产物完全不同，选错就白做。六条通用规矩：第一天就标清是一次性的、启动要极简（一个命令或双击）、默认不存数据、跳过打磨、每一步都把状态露出来、结束时要收（验证过的决定折回真代码，原型本身作为一手资料留在一次性分支上，并从实现票指过去）。

UI 分支还有两条硬要求：优先改已有页面，别新建空路由（空路由会掩盖设计问题）；变体之间不许共享布局、不许只改颜色文案。

/pr 模型可抓

PR 正文的形状：用最小的一张图讲清改动 + 前后证据 + 合并危险判断。

三段固定：摘要（挑最小的那个视图：伪代码 / 调用树 / 组件树 / 文件树 / 图 / diff）、证据（截图最好，执行证据次之，必须前后对比）、合并危险（单向门还是双向门 + 影响范围一个词）。客套话全删，用词表里的词。

它不替你写代码，只管正文形状。图要贴着它支撑的那段短文放，只留回答"当前这个问题"需要的东西。

快开 PR；或者要让别人（还有三个月后的你）三分钟看懂这个改动。

内部一次性提交。

/wizard 模型可抓

生成一个交互式 bash 向导，一步一步领人走"只有人能走"的流程，边开网页边把值抓进 .env 和 CI secrets。

"让人做"和"让人被领着做"是两件事。它把重复解释给 AI 的过程固化成脚本：分阶段进度、每阶段清屏只显示当前一步、确认闸门、跨平台开链接、隐藏输入密钥、重复跑也不会写坏 .env、写 gh secret、结束给摘要。模板永远不许手改，你只写阶段。

① 定范围（读 .env*、README、docker-compose、CI 配置，里面每个 secret 都是一个必须产出的值）→ ② 每个阶段写清"哪个网址、做什么、值在哪、填哪个变量"（不知道就说不知道，不许编步骤）→ ③ 一阶段一个 → ④ bash -n + shellcheck + chmod +x，不要自己端到端跑，静态追每个值都落地。

开通基础设施、配凭据 / CI secret、陌生的三方控制台、一次性迁移切换。

agent 自己能做的事——那就它自己去做，别做向导。

模板修了一批边角问题：回车保留当前值时不再把引号一起存进去；阶段跑在函数里，改脚本不会把正在跑的向导弄死；清屏失败有兜底；写 .env 时用单引号包值，空格、#、$ 和引号都能活下来；软链接的 .env 也能写进去并保留原权限；输入遇到 EOF 会报错而不是死循环。

/writing-fragments beta

/writing-shape beta

成型阶段：把素材逐段塑造成文章，每一步都在争"这块该用什么形式"。

它是"被反转的追问"：问题从"你在注意什么"变成"这篇到底在论证什么、读者该按什么顺序听"。核心概念是接地：每个概念要么是读者自带的，要么在前面某一块交代过；引用了没交代的概念就丢读者。要争的形式：散文还是列表、写在正文里还是抽出来做提示框、表格还是重复结构、引用还是转述、代码块还是行内。

先定前提 → 给 2-3 个候选开头（各自隐含不同论点）逼你选 → 逐块生长、每块落地就写进文件 → 每次写前重读。素材文件只读；素材缺东西要明说"这里需要例子，素材里没有，你现在给或者我们砍掉这段"。

还没探索够——回去 fragments。

/writing-beats beta

成型的另一种走法：把文章当成一串节拍，让你选路。

跟 writing-shape 同一个目标，但组织单位不同：节拍是旅程里的一个动作（设一个场景、落一个点、提一个问题、插一句旁白、扭一个角度），做完就停，让下一拍能转向。一拍按需要定大小，一句话也算。"需要五段三个小标题的那不是一拍，是两拍粘在一起。"

先定前提 → 给 2-3 个候选起手拍（各自入口不同，并说明各自交代了什么、解锁了什么）→ 只写选中的那一个 → 重读文件 → 给 2-3 个候选下一拍（必须都能从已经交代过的东西走到）。

/software-factory beta 新加的

给"软件工厂"这件事定一套共用词：它跑哪些任务、插哪些服务。

所谓软件工厂，就是"一堆 agent 把工单、PR、定时任务变成已合并的代码"，跑在你选定的远程机器上。这个技能只做一件事：把讨论它时该用的词定下来——任务（一种活，定义一次跑很多次）、触发（什么事件开始一次运行）、一次运行（一个任务在一个运行机上从触发到结束，当黑盒看）、运行机（一次性的机器，跑完什么都不留）、工单系统（人跟工厂的接口）、工单来源（反馈按钮、监控、报错平台）、代码托管、调度器、可观测平台。它会拦你用 job/workflow/session/server 这些词。

设计分两半：服务（每个位置填一个产品）和任务（这些运行怎么把活往前推）。它反复强调的三条刹车：自动检查、自动评审、人工评审；一次只加一个自动触发，先掐着量跑，人工评审每一单，等刹车可信了再放开。每个任务要答五个问题：什么触发它、它读写哪些服务、它接下来触发谁、人从哪重新进场、什么防止两次运行干同一件事。设计算完成的标准：每个位置都点了名（可观测平台可以明确说"不要"），每个任务和工单来源都答完了这几问。

你在琢磨"让 agent 自动处理工单 / 自动评审 PR"这种系统，需要跟人把它讲清楚。

你只是想让 agent 帮你做一次活——那是 implement 的事，不是建工厂。

/migrate-to-shoehorn 冻结

把测试里的 as 断言换成 @total-typescript/shoehorn 的 fromPartial() / fromAny()。

只针对测试代码（生产代码永远别用）。它解决两个具体的烦：一个巨大类型（一个有二十个字段的请求）里你只用到一个字段，却被迫造假二十个；以及故意传错数据时要写 as unknown as T 这种双重断言。

装包 → 搜测试文件里的 as → 普通断言换 fromPartial()，双重断言换 fromAny() → 跑类型检查。

TS 测试里 as 泛滥。

团队不接受新增依赖，或者本来就没几个 as。

七、四个典型场景，从头走一遍

场景里的目录名、文件名都是示意，重点是"产物落在哪、第几步别切会话"。这套方法一半的价值在产物位置。

场景 0：接口字段还没确定

要做的事：某个接口的字段、必填、取值、后端到底怎么算的，现在全靠猜。

先看清一件事：这不是一个技能能解决的，而是三种"事实"走三条路。

你要确认的东西事实在哪用什么拿到什么
第三方产品的官方行为（某个 API 怎么锁、参数怎么穿）官方文档 / 上游源码/research带引用的笔记
自家后端的字段名、类型、必填、取值、调用链、谁在写这个值后端代码派子任务取证：查调用链 + 在沙箱里搜，只回一张表字段证据表：字段 / 类型 / 必填 / 取值 / 出处（文件 + 符号）
代码看不出来的：为什么这么设计、历史包袱、契约还会不会变、什么时候上线后端的人/to-questionnaire一份问卷（把已经查到的证据放进背景，只问代码答不出的部分）

顺序：别把三条路并行乱走

  1. 先读仓库自己的约束：接口相关的约定、以及词表里这批业务词。这一步决定了后面所有命名。
  2. 再查代码：派一个子任务去后端仓库找证据，只回一张表。它要回答：这个字段在后端叫什么、什么类型、必填与否、取值从哪来、哪个接口返回、有没有被二次加工。原文不要进主上下文——真要看大段代码，就在沙箱里算完只打印结论。
  3. 只剩"代码答不出的"才去问人：把第二步的证据放进问卷背景，问题只问"为什么这么设计 / 会不会变 / 有没有坑"。别问"这个字段是什么"——那是能自己查的，问人就是浪费对方时间。
  4. 喂回追问：证据和问卷答案一起进 /grill-with-docs，让决定建立在事实上，而不是假设上。
  5. 落进 spec：/to-spec 的"实现决定"里写接口契约（字段含义、必填、取值），但不要写文件路径和代码片段——那些过期得最快。
取证时最容易踩的三条：
① 字段名照后端原样用——它叫 file_name 就写 file_name，别搞 file_name ?? fileName ?? name 这种猜测式兼容；
② 不要用假数据兜底——真接口接上之后，业务代码里不该留"失败就走假数据"的分支；
③ 结论要能复核——必须指得到"哪个文件、哪个符号、哪一行逻辑"，抽查式的结论算无效。

场景 A：一次跨模块搬迁（主线全走一遍）

要做的事：把几条业务线从老模块搬到新模块，牵涉接口、页面、菜单、权限。

  1. /grill-with-docs　把"搬过去"这个模糊动词问成五六个已经拍板的决定（5.6 那一轮就是它的真实形态）。
    产物：词表里新增或收紧的词；如果"模块归属"这条决定满足那三个条件，会提一条 ADR。
  2. /to-spec　不再问你，把上一轮合成 spec。它只会问你一件事：seam 放哪。
    正确回答：放在"取数入口的形状"和"节点来源"两处，而不是"每个页面各测一遍"。产物：.scratch/<特性>/spec.md，状态可开工。
  3. /to-tickets　切成竖片并标依赖。
    产物：issues/01-*.md（无依赖）、02-*.md（无依赖）、03-核对.md（被前两张卡着）。注意：如果"路由注册"这一改会同时炸到几十个页面，它就不是竖片，按"先加新的 → 分批搬 → 最后删旧的"拆。
  4. /implement 01　它先报出票标题，然后在说好的 seam 上跑 tdd。
    每轮：先写红测试 → 最小实现 → 类型检查 → 跑单个测试文件。别每轮都跑构建或全量检查。
  5. /code-review since main　两栏 review。规范那栏会读你的入口文件和规范文档；需求那栏会读刚才那份 spec。
    预期会命中的坏味道：Middle Man（为了搬迁新增的中转层）、Duplicated Code（三个页面又各写一份取数）。
  6. /pr　摘要用文件树 diff + 路由对照表；证据放迁移前后的菜单 / 权限截图；合并危险判"双向门 + 影响范围=路由/菜单"。
  7. /retro　在同一个会话里跑。正确的产出不是再写一篇文档，而是一条确定性检查：比如给"新增一级路由必须三处同步"写一个一致性测试。
关键判断：第 2 步之前别开新会话。追问 → spec → 拆票是一条思路，中间清掉，等于让 agent 拿着二手摘要重新推理。第 4 步起，每张票都可以开干净会话。

场景 B：一个难 bug（六阶段）

要做的事：切单据时有个监听没清掉，来回切几次就泄漏，但只在特定操作顺序下复现。

阶段做什么具体长什么样
第一阶段
造回路		造一条会红的紧回路。原文：这一步就是全部，没有它不许进第二阶段。一个单元测试：挂载 → 切换单据 → 断言监听数量回落到初始值。名字写成用户症状（"切换单据后不再监听旧单据"），不是"监听被正确清理"。要求：秒级、稳定、不用人盯。
第二阶段
复现+最小化		先确认红的是用户描述的那个失败；再逐个删输入、调用、配置，直到"去掉任何一个都变绿"。最小化到"只有连切两次才泄漏"这种程度——它能把第三阶段的假设空间从"整个模块"缩到"两次切换之间的清理时机"。
第三阶段
假设		先写 3-5 个可证伪的假设，每个都要说得出"如果 X 是原因，改 Y 会让它消失"，然后先给你看。你往往能立刻重排（"上周刚改过缓存返回那一块"）。
第四阶段
插桩		一次只改一个变量；调试日志加统一前缀；性能问题走另一条分支（先建基线再二分，不靠日志）。有调试器就用调试器，一个断点顶十条日志。
第五阶段
修 + 回归		在正确的 seam 写回归测试（能复现调用点上的真实模式）。没有正确 seam 本身就是发现：说明架构在阻止你把 bug 锁死。如果只能在最内层单测，而真实 bug 发生在"多个调用者串联"上，那是 seam 太浅，别硬写一个给你假信心的测试。
第六阶段
清理		原路径不再复现、回归测试过、调试日志清空、临时文件删掉、把"正确的那个假设"写进提交说明。然后同一个会话跑 /retro：问"什么环境能防住它"——大概率答案是缺一个一致性测试。

场景 C：架构体检 → 深挖一个模块（不是"重构全库"）

要做的事：几十个列表页长得几乎一样，改起来越来越绕。

  1. /improve-codebase-architecture　先定范围：看提交历史找最近改得多的区域，再派子任务自己去逛。用删除测试判断哪些是空壳。
  2. 读报告（写在临时目录，不进仓库）。每个候选看四件事：涉及文件 / 问题 / 方案 / 强度。它会告诉你"我先做哪个"。
  3. 选中一个 → 进追问：约束、依赖、收拢之后长什么样、seam 后面放什么、哪些测试能活下来。
  4. 想比较几种接口 → /codebase-design 的"设计两次"：并行 3 个以上子任务，各自一个激进不同的约束（入口最少 / 最灵活 / 最常见调用者最省事），最后按深度、改动集中度、seam 位置比较，并给出自己的推荐（别只摆菜单）。
  5. 落成方案 → /to-spec → /to-tickets。这类工作经常不是竖片，而是"先并存、再分批搬、最后删旧的"。
别做的事：不要指望它帮你"抢救"一个陈年老坑。原文说得很直接：它是体检，不是抢救。老代码库上它会找出真实候选，但不会替你把泥巴理顺。

报告里出现十几张卡之后：先别急着追问

十几张卡很常见，但一次只该挑一个——原文就是问"你想深入哪一个"，选中之后才进追问。对十张卡各跑一次完整追问，意味着你要回答五到一百个问题，而且每张卡的决策树活在不同会话里，切回去就断。

阶段做什么跑什么产物 / 提醒
0把报告存下来—临时目录会被清理；先复制到仓库里一个被忽略的目录（比如 .scratch/architecture-review/日期.html）
1归类 + 分三档：按根因合并（十张卡通常只有三四个根因），分成"现在做 / 以后做 / 不做"一个会话，不调追问"不做"的必须留一条理由，否则下次体检它还会冒出来
2只挑 1 张，优先挑位置最靠上游的那张（做完它，其他几张会变轻）/grill-with-docs → /to-spec → /to-tickets，一张卡一个会话spec 加票就是交接物，下个会话不需要记得这次聊了什么
3逐票实现/implement <票>（每票一个新会话）内部会跑 tdd 和 code-review
4回到阶段 1 选下一张；做完的回填一行结论—全部做完后重跑一次体检
唯一的例外：当这些卡互相依赖，或者"先做哪张"取决于"做完上一张才知道什么"——这时"路线"本身就是未知的，该跑 /wayfinder，地图清楚之后再接 /to-spec。
一句话判据：卡与卡互不依赖 → 逐张追问；卡之间得先排路线 → wayfinder。

深模块 / 浅模块，五问就能判

别用行数判断。下面五问，任一条答得别扭，就是浅模块或者假抽象。

#问自己深的模样浅的模样
1删除测试：删掉这块，复杂度是消失还是散开？散回 N 个调用点 → 它在挣饭吃复杂度直接消失 → 它是纯中转
2调用者要学多少：用对它要读几个文件、知道几件事？一个入口 + 少量参数 + 明确的出错方式要读三四个文件，还得知道"先调 A 再调 B"
3改动集中吗：改一条业务规则要动几处？一处，改完全局生效散在页面里，改三十处
4能不能只通过接口测？只断言接口行为必须 mock 内部，或者必须查库旁证
5能不能用领域词命名（词表里有词吗）？能，比如"对账单""结算规则"只能叫 useXxxPage，说明抽象错位了

两个反直觉的结论：①大不等于深——两千行的巨型文件只是大；深是小接口 + 大行为 + 干净的 seam。②"多一层"不等于深——把一行赋值包进函数、再包进 hook、再包进组合式函数，删除测试会说"复杂度消失了"，这是假深化。

"AI 会自己遵循深模块吗？默认不会。"代码生成是局部最优，深模块是全局约束。四个把手按有效程度排：
① seam 写进 spec（/to-spec 会强制你确认，这是唯一卡在流程里的点）；② review 的规范那栏（把"禁止没依据的兜底 / 禁止纯中转"作为标准喂给它）；③ 确定性检查（一致性测试 / lint / 依赖规则）；④ 词表（先有能命名的词，才可能有对应的模块）。
结论：别指望它理解深模块，要让它没机会写浅模块。

场景 D：雾很大的活（wayfinder）

要做的事：路由注册、权限推导、左侧菜单数据源要统一，跨三个入口，牵一发动全身。

  • 画地图：先追问给目的地起名（"让新增一个一级页面只改一处，且不再出现权限有、菜单没有"）；然后横着再问一轮，扫出还开着的决定。
  • 建地图：.scratch/<这摊活>/map.md，五节：目的地 / 备注 / 已定的事 / 还没说清 / 范围外。如果仓库里已经有一份执行看板，地图里用一句话指向它，不要复制一份。
  • 建票：issues/01-*.md、02-*.md…，每张写清类型（研究 / 试验 / 追问 / 事务）和被谁卡着。能说精确的才建票，说不精确的放进"还没说清"。
  • 走地图：一次只解一张，先认领再动手；解完写结论、关票、往"已定的事"追加一行。研究票可以并行，派子任务去读官方行为。
  • 交棒：雾散之后接 /to-spec，不要直接 implement——地图里链接起来的细节会被丢掉。

八、上下文该清、该接、还是该派出去

阶段是会话里的一段工作（追问、实现、验收）。边界只在"行，这块结束了"的那一刻存在。别在阶段中间做这个决定——中期只有两个选择：继续，或者把剩下的活切成子任务。中期压缩会让 agent 丢掉线索。

选项它做什么代价什么时候
继续什么都不换。下一段需要这一段当一手材料，或者你还有足够的余量（大约 150k）。窗口更满追问 → 实现是标准答案：实现要的是你推理的原话，不是它的摘要。这条要第一个排除。
清空窗口清零，从头开始。不可逆地丢掉"为什么"前面全是探索、死路、可以丢的上下文。它最便宜，而且旧会话还能恢复。
/handoff写一份能带走的 md，在任何地方种下新会话。有损；多一个文件只有四种情况：换工具、换目录 / 仓库、交给同事、在阶段中途分叉副任务。买的是"能搬走"；没东西要搬，就不需要它。
派子任务把活放进它自己的窗口，拿回一份报告。你要等报告这件事能不用人盯地做完（自动 review 是标准案例）。
压缩把这一段压掉，种下新会话。摘要会抹平决定默认项，但不是首选：相关、同工具、同目录、而且你必须留在环里。给一句指令（"压缩，接下来我们要做验收"）让摘要保住下一段要的东西。

顺序（第一个"是"就赢）：① 能继续吗（需要它当一手材料 / 还有余量）→ ② 上下文跟下一段无关吗（清空）→ ③ 需要交接吗（handoff）→ ④ 能不用人盯地做完吗（派子任务）→ ⑤ 否则压缩。

核心取舍：除了"继续"，每个动作都在把一手材料换成二手材料——原始会话被它的摘要替代。一手信息全、噪音多、腾挪空间小；二手有损、噪音少、腾挪空间大。所以第一个问题永远先问"能不能继续"：只有留下来的成本高于换掉时，才付这份有损的代价。

落到日常的建议

场景建议
追问 → spec → 拆票同一个窗口，不要清。
票与票之间清空。每张票是自包含的，上一张的上下文是垃圾。
写代码 → 验收测试同一个窗口继续，或者压缩（"接下来做验收"）——验收需要知道"为什么这么实现"。
改到一半被叫去查线上问题派子任务去诊断，或者 handoff 分叉，主线不动。
要换到另一个工具继续/handoff。这是它唯一不可替代的场景。
1.3.2 补的一条细节：凡是会派子任务的技能，现在都明确要求"给每个子任务开一个新的干净窗口"，不要从当前对话 fork 出去。因为有些客户端（比如 Codex）默认就是 fork，而 fork 恰好把它本来该有的干净上下文扔掉了——子任务存在的意义就是"不带你的包袱去看"。

九、跟你仓库里已有的规矩撞了怎么办

这套东西默认只带"做法"，你仓库里的入口文件带的是"边界"。真撞上了，边界赢——但你必须写清楚谁覆盖谁，否则 agent 会照着技能的原文执行。下面几条是最常见的撞法。

看着像冲突怎么撞的结论 / 怎么合
深模块 vs 反过度封装 /codebase-design 鼓励"把大量行为藏到小接口后面"，你的规矩禁止"没意义的中转函数、多层封装"。 不冲突，是同一把尺子。原文明说：深度是接口的属性，不是实现的行数；并给了删除测试——删掉它，复杂度消失=纯中转（该删），复杂度在 N 个调用点重现=它在挣饭吃（该留）。你禁止的正是"删除测试为负"的那类。把删除测试写进你的约束文档，两边就统一了。
tdd 收尾跑全量 vs 禁全量 /implement 说"最后跑一次全量测试"，你的规矩说"别默认跑全量检查"。 按场景收窄：开发期每轮类型检查 + 单个测试文件；收尾只跑受影响的目录，不做完整构建，除非你明确要求。把这条写进技能的调用说明里就行。
坏味道基线 vs 项目文档 基线里有"为不存在的需求预留抽象"，而你的项目有时确实要为已知需求留位置。 原文已经给了优先级：仓库文档永远压过基线，坏味道永远只是"可能是"、不是硬违规，工具已经强制的直接跳过。所以命令是：/code-review since main，规范那栏额外指定你的入口文件和治理文档。
它会顺手改词表 你担心它把你的词改坏。 这正是它该做的事，前提是你的词表本身合规（只收领域词、写明哪些词要避免、不写实现细节）。唯一要守死的一条：词表里绝不写实现。要写实现，那是提 ADR 或写 spec。
和你已有的开发技能功能重叠 你的技能里可能已经内置了追问 + tdd，两边都跑就是双重拷问。 按触发条件分工：你指名"按架构规范开发"就走你自己那个；普通业务需求走 /grill-with-docs。不要串着跑两次追问。可以做的改造：让你那个技能内部调用 grilling / tdd，而不是各写一份纪律。
技能里的 shell 命令 vs 你的工具规矩 技能里用 git diff、grep、git log，你要求所有大输出走沙箱或者加前缀。 冲突范围比看上去小得多。真正会踩线的只有一种情况：大段文本被灌进主上下文。技能里的命令本身很窄（git log --oneline、git diff --stat），/code-review 更是把整段 diff 交给子任务去读——子任务的窗口是一次性的，压不压缩无所谓。所以只需要守一条行为：重文本不进主上下文。
retro 建议新建一份标准文件 你已经有自己的规则文档，不想再多一份。 不新建。把它当"是不是有好几份真相"的检查：如果发现同一条规则散在三处，合并进现有文档；机械性的违规一律做成 lint 或测试，而不是再加一篇 md。
triage 会写"范围外"记录 你仓库里没这个目录。 只在真的否掉一个需求时才建（用到才建）。bug 的拒绝不写；"已经实现了"的拒绝更不能写（会污染去重）。
tdd 和验收测试的分工 两个都在谈测试。 阶段不同：/tdd 是开发期在 seam 上锁行为；验收测试是交付前那一层（代码级 / 接口冒烟 / 浏览器巡检 / 人眼清单）。顺序：tdd → code-review → 验收。
技能建议开 PR / 提交 你仓库里没有 PR 流程，也不允许随手提交。 按项目覆盖：/implement 最后那步"提交"仍然要你明确要求；/pr 只在真要开 PR 时用，平时跳过。这些覆盖要写进入口文件，别靠记。
一句话原则：技能提供的是做法，你的入口文件提供的是这个仓库的边界。冲突时边界赢——但必须显式写出覆盖，否则 agent 默认照技能原文执行。

10.5 如果只做三件事

① 把 /grill-with-docs 变成默认起手式

任何不琐碎的需求，第一句就是它。它同时治"它没做我要的"和"它话太多"这两个毛病，而且是唯一一个顺手把词表建起来的入口。回报最高，成本几乎为零。

② 把 /retro 的产物变成检查，不是文档

再写一篇规范的边际收益很低。真正的收益在把"同一类错第三次发生"变成一条 lint 规则、一个一致性测试、一个 CI 任务。文档只留给需要判断的事。

③ 只守一条：大段文本不进主上下文

不用改入口文件，也不用逼 agent 每条命令都加前缀。真正要守的只有一件事：大段 diff、日志、后端代码不要灌进主上下文——交给子任务，或者在沙箱里算完只打印结论。这一条同时解决了"技能里命令怎么写"和"上下文被撑爆"两个问题。

  • 上游发版时：读 CHANGELOG.md → 只改受影响的卡片 → 在这一页顶部更新版本号。
